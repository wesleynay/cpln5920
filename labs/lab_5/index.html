INTRODUCTION

The Rebalancing Challenge in Philadelphia

Philadelphia’s Indego bike share system faces the same operational challenge as every bike share system: rebalancing bikes to meet anticipated demand.

In this report, I adapt the in-class Q1 2025 exercise to Q3 2025 because I am interested in a seasonal comparison between winter and summer. Using station-hour panel data, weather data, census tract characteristics, and lagged demand measures, I build and compare several predictive models for bike share demand. I then examine where the model performs well, where it struggles, and whether prediction errors have operational or equity implications.

Research Goals

This analysis addresses four main questions:

  1. How do bike share demand patterns in Q3 2025 differ from the in-class Q1 2025 example?
  2. Which model features improve predictive accuracy the most?
  3. Where are prediction errors concentrated across space, time, and neighborhood context?
  4. Can targeted feature engineering improve model performance in a meaningful way?

Create Time Bins

Next, I need need to aggregate trips into hourly intervals for my panel data structure. I will use the lubridate library for the date/time data extraction.

Code 
indego <- indego %>%
  mutate(
    start_datetime = mdy_hm(start_time),
    end_datetime = mdy_hm(end_time),
    interval60 = floor_date(start_datetime, unit = "hour"),
    week = week(interval60),
    month = month(interval60, label = TRUE, abbr = TRUE),
    dotw = wday(interval60, label = TRUE, abbr = TRUE),
    hour = hour(interval60),
    date = as.Date(interval60),
    weekend = ifelse(dotw %in% c("Sat", "Sun"), 1, 0),
    rush_hour = ifelse(hour %in% c(7, 8, 9, 16, 17, 18), 1, 0)
  )

The interval60 variable is the backbone of the panel structure. It rounds each trip down to the beginning of the hour, making it possible to aggregate all trips that started within the same hour at the same station. This is what allows the analysis to move from individual trips to station-level hourly demand.

CREATE TEMPORAL LAG VARIABLES

The key innovation for space-time prediction: past demand predicts future demand.

Why Temporal Lags?

Temporal lags are especially important in a bikeshare context because demand is often persistent. If a station had high demand one hour ago, it is more likely to have elevated demand now than a station with no recent activity. In other words, temporal dependence helps the model capture short-run demand momentum.

Code 
# Sort by station and time
study_panel <- study_panel %>%
  arrange(start_station, interval60)

# Create lag variables WITHIN each station
study_panel <- study_panel %>%
  group_by(start_station) %>%
  mutate(
    lag1Hour = lag(Trip_Count, 1),
    lag2Hours = lag(Trip_Count, 2),
    lag3Hours = lag(Trip_Count, 3),
    lag12Hours = lag(Trip_Count, 12),
    lag1day = lag(Trip_Count, 24)
  ) %>%
  ungroup()

# Remove rows with NA lags (first 24 hours for each station)
study_panel_complete <- study_panel %>%
  filter(!is.na(lag1day))

TEMPORAL TRAIN/TEST SPLIT

CRITICAL: We must train on PAST data and test on FUTURE data!

Why Temporal Validation Matters

In real operations, at the start of September, we would need to predict demand for the rest of the month using only the data available from July and August. We wouldn’t have access to future data because it hasn’t happened yet.

Wrong approach: Train the model on later weeks (e.g., late September) and test it on earlier weeks (e.g., July and August). This would mean using future information to predict the past.

Correct approach: Train the model on earlier weeks (July through mid/late August) and test it on later weeks (late August through September). This ensures that we are using past data to predict future demand, which better reflects how the model would be used in practice.

Code

FEATURE ENGINEERING AND MODEL IMPROVEMENT

Next, I will add 2 new features to improve my model.

Feature 1: Same Hour Last Week

Because the lag variables improved the model the most, I decided to add another temporal demand feature: the same hour last week. This helps capture weekly travel routines that a 1-hour or 1-day lag may miss. For example, demand at 8 AM on a Tuesday is probably more similar to 8 AM on the previous Tuesday than to some other recent hour.

Feature 2: School-in-Session Indicator

I also added a school-in-session indicator because Q3 includes the transition from summer into the fall semester. In a city like Philadelphia, universities likely shape bike share demand, especially near Penn, Drexel, and Temple. This feature helps the model account for the seasonal return of students and campus activity.

# CREATE TEMPORAL LAG VARIABLES

The key innovation for space-time prediction: **past demand predicts future demand**.

## Why Temporal Lags?

Temporal lags are especially important in a bikeshare context because demand is often persistent. If a station had high demand one hour ago, it is more likely to have elevated demand now than a station with no recent activity. In other words, temporal dependence helps the model capture short-run demand momentum.

```{r create_lags}
# Sort by station and time
study_panel <- study_panel %>%
  arrange(start_station, interval60)

# Create lag variables WITHIN each station
study_panel <- study_panel %>%
  group_by(start_station) %>%
  mutate(
    lag1Hour = lag(Trip_Count, 1),
    lag2Hours = lag(Trip_Count, 2),
    lag3Hours = lag(Trip_Count, 3),
    lag12Hours = lag(Trip_Count, 12),
    lag1day = lag(Trip_Count, 24)
  ) %>%
  ungroup()

# Remove rows with NA lags (first 24 hours for each station)
study_panel_complete <- study_panel %>%
  filter(!is.na(lag1day))
```

# TEMPORAL TRAIN/TEST SPLIT

**CRITICAL:** We must train on PAST data and test on FUTURE data!

## Why Temporal Validation Matters

In real operations, at the start of September, we would need to predict demand for the rest of the month using only the data available from July and August. We wouldn’t have access to future data because it hasn’t happened yet.

Wrong approach: Train the model on later weeks (e.g., late September) and test it on earlier weeks (e.g., July and August). This would mean using future information to predict the past.

Correct approach: Train the model on earlier weeks (July through mid/late August) and test it on later weeks (late August through September). This ensures that we are using past data to predict future demand, which better reflects how the model would be used in practice.

```{r temporal-split}
# Split by week
# Q3 has roughly weeks 27-40 (July-Sep)
# Train on weeks 27-38 (July through most of September)
# Test on weeks 39-40 (late September)

# Which stations have trips in BOTH early and late periods?
early_stations <- study_panel_complete %>%
  filter(week < 39) %>%
  filter(Trip_Count > 0) %>%
  distinct(start_station) %>%
  pull(start_station)

late_stations <- study_panel_complete %>%
  filter(week >= 39) %>%
  filter(Trip_Count > 0) %>%
  distinct(start_station) %>%
```
